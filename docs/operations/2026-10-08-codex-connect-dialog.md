# Codex 会话连接弹窗的机器与请求生命周期

用户反馈 Lis-iMac 会话能搜索出来，但点击“连接并打开”后没有进入聊天。截图中的表单已经显示 CHRIS，弹窗列表为空，却仍显示一个选中项且允许提交。

后续从原始 Hub/Nginx 与 Windows Runner 日志追查了这次请求，并拆分旧清理过程的 19 次同步调用。原始事故时序、证据边界及新发现的跨机器时钟问题见 [根因调查](./2026-10-08-windows-connect-root-cause.md)。

## 复现与修复

`/api/machines` 只返回在线机器。`NewSession` 以前发现当前机器不在返回列表里，就自动选择另一台机器。机器 ID 改变触发 Codex 列表重置和连接 generation 失效，导致正在进行的连接成功或错误都被忽略。弹窗自己的选择状态没有随列表失效，因此出现空列表仍可提交的状态。

目录更新也会使同一重置 effect 执行，虽然跨目录的会话搜索与正在连接的原生 thread 并不依赖创建表单目录。旧版后续页响应还会根据新一页的 ID 清除早先页面的选择。

修复后的机器默认选择只在尚未选择时执行。离线机器保留名称和 ID，明确显示离线状态；不自动改成其他机器。机器离线期间不允许发起新建或新的 Codex 连接请求，已发出的请求仍处理确认结果和错误。用户明确换机器、换 agent、关闭弹窗或卸载表单时，旧请求仍按 generation 取消展示，避免晚到结果打开错误会话。

会话列表与连接任务按机器和 agent 定界，目录变更不再清空它们。真实机器或 agent 变更关闭旧弹窗、清除其机器绑定和选择。连接只能提交当前列表中的可连接 thread，并使用列表的明确机器绑定。弹窗即时根据当前列表计算有效选择；移除或变为不可连接的 thread 不再显示为已选，也不能再次提交。后续页追加保留早先页面的有效选择。

原生 thread 的连接、恢复、模型生成请求、历史存储和权限检查保持原有行为。Hub 未修改。Windows Runner 另外修复了下述模型目录查询造成的阻塞。

## Windows Runner 的同步阻塞

真实接口还出现过 `operation has timed out` 的 503。`NewSession` 同时查询 agent、模型目录和会话列表；旧的模型目录缓存失效时，会启动一个临时 `codex app-server`。其 `disconnect()` 调用 Windows 进程树清理，包含同步 `tasklist` 和 CIM 查询，运行在 Runner 的事件循环上。

在同一个后台账户、Session 0 中，用独立探针执行这条旧代码路径，避免主动阻塞线上 Runner。模型结果在 10,058 ms 已收到，清理到 57,184 ms 才完成；20 ms 定时器观察到最长间隔 47,096 ms。这足以使并行 RPC 超过 30 秒超时或机器心跳过期，但它不是用户原始点击时的网络抓包。

原生安装的模型目录查询改为经过现有认证桥接发送只读 `model/list`，断开时只关闭这个客户端连接。沿用模型归一化、五分钟缓存、隐藏模型分槽及并发请求合并，不启动临时 app-server。未配置同账户桥接的普通 CLI 安装仍沿用原来的用户主目录查询；已配置但失效、多个匹配桥接或无法验证身份时返回错误，不降级启动新进程。可选发现按已有 strict 读取方式检查记录，认证和进程创建时间验证均保留。

新版独立探针的可见模型冷查询为 3,279 ms，缓存命中为 0 ms，隐藏模型冷查询为 2,987 ms；最长事件循环间隔为 22 ms。部署前再运行一次探针，冷查询分别为 2,218 ms 和 2,180 ms，最长间隔 45 ms。两次均未创建 Codex 引擎或发送模型生成请求。
