# 工作区反复切换：内存持有链修复与测量

2026-10-06，前端已发布。此次解决工作区切换后旧聊天 DOM 无法回收的问题，保留既有阅读位置、草稿、分页和移动列表行为。完整 tmux 目标尚未完成，终端开发继续按用户要求暂缓。

## 复现与原因

使用编译后的真实 App 和受控 Hub fixture：12 个工作区，每个会话有 320 条记录，最后一条回答含 1,500 行 TypeScript。第一轮在每个会话写入独立草稿并滚到不同源字符；随后反复返回，检查同一个字符的屏幕位置和草稿。工作区之间切换不更换页面路由。

旧版三个独立浏览器上下文均复现：经过五轮访问，强制回收后仍有 54,385 个 DOM 节点，页面实际只显示 1,720 个节点。堆快照发现两条持有链：

1. Router 的全局订阅 → `trackedScrollEntries` → 每个曾滚动过的旧窗格。该集合只在路由导航时清空，工作区内部切换不会触发清理。
2. 长期保存的阅读书签 → `capturedTextNodes` → 原来的文本节点 → 旧聊天 DOM。这里的 WeakMap 只弱引用书签这个键，书签仍在保存时，其值中的节点也是强引用。

核对的 [TanStack Router 上游源码](https://github.com/TanStack/router/blob/main/packages/router-core/src/scroll-restoration.ts) 仍以强引用集合跟踪滚动目标，并在路由事件中清空；本地使用的版本为 1.171.6。本次以 Bun 的版本化依赖补丁，在注册新滚动目标时释放已经脱离文档的目标。仍连接的列表继续保留滚动位置；已有目标的每次滚动不扫描集合。

HAPI 的同节点定位捷径改用 `WeakRef<Text>`：文档仍挂载时可以精确复用节点；卸载后，书签不再拥有整棵旧 DOM。语义位置、引文匹配和 CodeMirror 源字符恢复保持原有逻辑，无存储格式变更。

## 测量结果

Chromium 153.0.8010.12，1600×960。前后各三个独立上下文、每次五轮；除首次设置外，各有 144 次被计时的恢复。构建、测试和堆快照采集没有与正式计时样本同时运行。

| 指标 | 原发布版 | 修复版 |
| --- | ---: | ---: |
| 同一源字符最大偏差 | 0 CSS px | 0 CSS px |
| 恢复耗时中位数 | 372 ms | 359 ms |
| 恢复耗时 P95 | 808 ms | 811 ms |
| 最慢恢复 | 899 ms | 991 ms |
| 最后一轮回收后 JS 堆，中位数 | 56.41 MiB | 44.20 MiB |
| 最后一轮仍存活 DOM 节点 | 54,385 | 4,215 |
| 页面实际 DOM 节点 | 1,720 | 1,720 |
| 挂载的窗格／消息行／代码行 | 1／7／92 | 1／7／92 |

这组数据支持旧视图释放和内存占用降低，不支持宣称恢复速度明显提升。计时从实际 DOM 点击开始，到原源字符恢复至 2 CSS px 以内为止，包含自动化查询开销；不包含 Playwright 点击前的可操作性等待。它也不是手机网络或物理设备性能。

另外单独执行十二轮诊断，共检查 132 次返回。DOM 节点自第二轮起一直为 4,215。第二轮至第十二轮的 JS 堆从 42.88 MiB 增至 46.42 MiB；对应快照中 V8 `code` 类增加 3.25 MiB，普通 `object` 只增加 3,676 字节，`array` 减少 26,660 字节。残余增量主要表现为引擎代码，不再是旧窗格逐个累积。该诊断包含堆快照，耗时没有并入上表。

fixture 将所有会话正文固定保存在浏览器内，因此上述堆值包含模拟服务器的成本；它不是浏览器进程 RSS。固定 12 个会话的反复切换也不代表任意数量的不同会话已经有统一内存上限：消息窗口状态与有界历史页缓存是不同层，仍须另测持续新增会话的情形。
