# Lis-iMac 原生 Codex 连接失败：原始日志与根因

用户先反馈会话列表一直加载，随后反馈能够搜索但“连接并打开”失败。第二张截图的创建表单已经变为 CHRIS，弹窗列表为空，却仍保留一个选中项。本次追查区分原始请求日志、独立性能探针和受控浏览器复现，不把后来测试成功当作原始事故已经解释。

## 原始请求时间线

Hub journal 与 Nginx access log 中，用户浏览器请求来自同一 Tailnet 地址和同一 Edge UA，与本机 Node、HeadlessChrome 验收请求可以区分。以下时间为 Hub UTC；第二张截图上传于 11:08:31 UTC。

| 时间 | 当时记录 |
| --- | --- |
| 11:07:22.882 | 浏览器请求 Lis-iMac 的 agent、模型目录及路径检查。 |
| 11:07:23.563 / 23.632 | agent 和路径请求分别在 681 / 750 ms 返回成功。 |
| 11:07:24.362 → 26.537 | 会话目录请求成功，耗时约 2.2 秒。说明此时列表已经恢复，后面的连接失败不能继续归因于列表扫描。 |
| 11:07:31.022 → 11:08:01.171 | 原始 `POST /api/codex/connect-session` 等待 30.149 秒后返回 503。这是真实用户请求，不是故障注入。 |
| 11:07:45.381 起 | 同一浏览器开始请求 CHRIS 的路径检查，符合截图中的机器被自动替换。 |
| 11:08:13 | Nginx 对仍在等待的 Lis-iMac 模型目录请求返回 502；Hub 的该请求最终在 11:09:22.884 达到 120 秒 RPC 超时并记录 500。两个状态属于不同层的等待终止。 |

Windows Runner PID 1689460 的日志另有：

```text
[19:07:06.732] List Codex models request
[19:07:06.793] [CodexAppServer] Starting codex app-server
[19:07:06.800] [CodexAppServer] Connected
[19:07:50.478] [CodexAppServer] Disconnected
[19:07:50.488] [API MACHINE] Disconnected from bot
[19:07:51.693] [API MACHINE] Connected to bot
```

这些是 Windows 本地 UTC+8 时间，不能直接减八小时后当作与 Hub 完全同步。三次只读时钟对照发现 Windows 比 Linux 慢约 16–17 秒；采样有约两秒 SSH/PowerShell 往返成本，保留原值和上下界，不伪造毫秒级校准。模型目录入口的时间差也与这个偏差相符。按该偏差估计，临时客户端断开和 Runner 断线发生在 Hub 11:08:06–08 附近，与连接请求的 30 秒等待重合。

原始日志没有逐个同步系统命令的计时，没有保存当时的 SSE `machine-updated` 帧，也没有为连接 POST 保存请求正文或贯穿 HTTP/RPC 的关联 ID。因此具体原生 thread 和离线帧的精确时刻不能从历史记录补造。原始 HTTP 超时、Windows 模型查询/临时进程/断线顺序与以下源码机制、独立复现共同支持因果判断。

## 主因：把 Windows 同步进程清理放在 Runner 事件循环

旧的模型目录查询在五分钟缓存未命中时创建临时 `codex app-server`，收到模型结果后仍要等待 `disconnect()` 清理进程树才能返回。清理代码声明为 async，但其中的进程树枚举、存活查询、创建时间查询和 taskkill 使用 `cross-spawn.sync`。这些调用会阻塞承载 RPC、Socket.IO 和心跳的同一事件循环。

在同一 Windows 后台账户、Session 0 下运行独立探针，逐个记录旧清理函数的调用。探针只创建自己的临时 app-server，发送 initialize 与只读 model/list；生产 Runner 与现有 Codex 会话没有参与这个阻塞实验。

| 同步工作 | 次数 | 合计耗时 |
| --- | ---: | ---: |
| CIM 进程树枚举 | 1 | 6,636 ms |
| tasklist 存活检查 | 13 | 27,724 ms |
| CIM 进程代际检查 | 3 | 7,831 ms |
| taskkill 清理探针自己的进程树 | 2 | 3,980 ms |
| 合计 | 19 | 46,171 ms |

模型结果在 2,834 ms 已经收到，清理从 2,835 ms 到 49,040 ms；20 ms 定时器观察到最长事件循环间隔 46,186 ms。此前未细分的独立探针也观察到 47,096 ms 的间隔。问题是同一循环连续执行大量同步系统查询，不是模型生成慢，也不能通过把单个同步命令的超时限制为 10 秒解决：19 个正常返回的调用仍可累积超过 30 秒 RPC 与 45 秒心跳期限。

模型请求单独配置的 120 秒 RPC 超时也没有保护其他 30 秒 RPC 或 Socket.IO 心跳。一旦连接断开，旧 socket 上的确认不能在新 socket 上自动交付，出现机器后来又在线、原请求仍然超时的现象。

已上线的修复在原生安装中使用现有认证桥接调用 model/list，关闭客户端连接即可，不再为这个目录查询创建与清理引擎。新路径独立探针最长事件循环间隔为 22 / 45 ms，生产并行模型和会话查询三轮约 2.1–2.3 秒。身份、认证、进程代际与多桥接歧义检查均保留。

通用 Windows 进程终止函数本身仍包含上述同步查询。这次上线消除了原生模型目录和会话筛选的常见触发路径，没有完成所有进程管理调用的异步化；实际终止进程的路径不能被这些验收结果代替。

### 100 ms 要求下的查询成本

用户进一步要求查询在 100 ms 内完成。2026-10-08 在相同后台账户、Session 0 对同一生产桥接 PID 做只读测量：

| 查询方式 | 实测 |
| --- | ---: |
| PowerShell 空脚本子进程启动 | 339.535 ms |
| 已运行的 PowerShell 内执行 CIM 单 PID 查询，三次 | 2,125 / 2,123 / 2,186 ms |
| 启动 tasklist 并查询同一 PID | 2,185.683 ms |
| .NET Process 直接取 Windows 进程创建时间，首次 | 4.073 ms |
| 同一直接查询，100 次中的 P50 / P95 | 0.014 / 0.023 ms |

这修正了“只是启动 PowerShell 慢”的判断：CIM/WMI 查询本身也是约两秒的主要开销。改成一次异步 CIM 只解决串行阻塞，不会让该次查询达到 100 ms。直接进程 API 的创建时间保留 100 ns 精度；截断至 CIM 的微秒精度后，与现有运行记录标记完全一致，具备保留 PID 代际校验的实现基础。

上述数据是接入原生查询之前的基线；当时生产 HTTPS 目录仍需 3,043 / 2,833 / 2,706 ms。随后已将原生查询接入 Runner，发布 `process-markers-v5.exe` 和配套目录改造。底层单函数的 0.023 ms 不代表整个流程达标，以下分别记录本机 RPC、HTTPS 和浏览器结果。

### 原生查询移植中暴露的真实权限边界

生产 Runner 使用 Session 0 的 LUA 受限令牌。一份过期运行记录中的 PID 1482952 已退出，但其进程对象仍被其他句柄持有。这个令牌下 `OpenProcess` 返回 access denied，而高权限探针能打开同一对象并检查出已退出。早期 C 查询器在写出半个数组后报错，造成 `JSON Parse EOF` 和查询器反复重启，继而使目录的全部连接状态变为不可用。

修复使用完整的逐行 JSON 响应：OS 查询错误只拒绝该请求，传输错误才关闭查询器。遇到 access denied 时，以本次请求的新鲜 `EnumProcesses` PID 集合确认进程是否仍存在；只忽略已经消失的 PID，活着但不可读的进程继续失败。每次查询仍重新打开进程句柄、核对创建时间，不缓存身份或绕过验证。此前 Toolhelp 逐 PID 快照的版本也被实测淘汰：它恢复了功能，却增加约 350 ms；请求共享一次快照仍超过预算，最终才采用 PID 枚举。

查询器随 Runner 初始化一次，以 stdio 接收后续查询；每次启动外部查询器本身仍会花 100 ms 左右，因此不能把本机 API 很快误认为重复启动也很快。真实 Windows 集成测试只改动测试自行创建的进程，覆盖创建时间格式、保留退出句柄、拒绝读取活进程、该进程退出后的目录处理。限制令牌下测试通过。这里还修正了测试条件：本机 S4U 计划任务即使设置 `RunLevel Limited`，也可能保留管理员能力；验收经现有 `HapiTaskHost` 创建与 Runner 相同的 LUA 令牌执行。早期更新脚本中的直接 S4U 预检属于补充数据，不能替代这个验收。

目录查询现在在一次 RPC 内共享 SQLite 连接和标题索引，对重复 cwd 合并权限解析并并行检查不同目录；下一次请求重新检查真实路径，符号链接变更仍能被拒绝。连接现有会话直接按完整原生 ID 查询数据库，不再先扫描所有会话。Windows 的 agent 可用性查询不再同步启动 `where.exe`，使用现有可执行文件位置与 PATH/PATHEXT 文件查找。

### 冷进入的额外主因：Hub 定时消息统计选错索引

冷进入创建页会并行请求 HAPI 会话列表、机器、模型和原生目录。浏览器记录显示普通 `/api/sessions` 也需约 200–260 ms，故不能把这段等待全部归因于 Windows。

生产数据库的只读 `EXPLAIN QUERY PLAN` 证实，两次定时消息统计选择了 `idx_messages_local_id`，扫描已经交付的消息。69 个会话的一次统计需 66–80 ms，两次查询阻塞承载所有 HTTP/RPC 的 Hub 循环。显式使用已有 `idx_messages_scheduled_pending` 后，同一查询为 0.012–0.126 ms，结果同为零组。未增加索引、改写历史或建立正文副本。回归同时验证统计语义和实际查询计划，防止重新扫描已交付历史。

| HTTPS 原生目录，30 次 | P50 85.4 ms，P95 119.0 ms，最大 364.0 ms | 第一条含 Hub 重连后的额外开销；不声称全部小于 100 ms |

浏览器预读从用户选择机器/agent 时开始，同一目录的在途请求和最近 5 秒结果复用。真实连接仍重新验证身份与 workspace 权限。搜索 debounce 从 250 ms 改为 25 ms，全文索引查询和既有增量分页保留。后端错误现在按真实原因回传，不再被成功响应的 Zod 校验改写成“缺少 sessionId/threadId”错误。

首开布局的焦点简化候选未证明改善，已撤回且未发布。仍需优化首次绘制与尾部延迟，不能以 DOM 已出现、暖缓存很快或平均值掩盖未达成的 100 ms 要求。

另一个已验证但不是这次第二张截图的持续触发点，是旧 `nativeCodexEligibility()` 对 18 份运行记录逐条同步检查 PID：独立探针约 70 秒。该处在 10:57 UTC 的第一轮 Runner 更新中改为预筛选加一次异步 CIM 查询，随后真实用户的 11:07 会话目录已在约两秒成功返回。两处缺陷具有相同的底层错误：把 Windows 外部进程查询当作廉价同步函数使用。

## 前端把后端失败放大为错误目标与丢失错误

旧 `NewSession` 发现在线机器列表中没有所选 Lis-iMac，就自动改选 CHRIS。机器 ID 变化会清空 Codex 列表，并使正在连接的 generation 失效。因此随后到达的 503 或成功确认都被当作旧请求忽略。弹窗自己的选择又独立于当前列表，留下“空列表、一个选中项、仍可提交”的状态。

这条前端路径已经在旧生产构建中受控复现，与截图及原始浏览器开始请求 CHRIS 的时序相符。没有原始浏览器的内存快照，不能声称直接记录到了那一次 effect 执行。

已发布的改动保留所选机器的身份与离线状态，不自动换机器；短暂离线不取消已发出的连接结果。只有用户明确更换目标或关闭页面时才取消展示。当前有效列表决定实际可提交的选择。原生会话恢复和消息发送逻辑保持原有行为。

源码：[NewSession](../../web/src/components/NewSession/index.tsx)、[选择弹窗](../../web/src/components/CodexSessionSyncDialog.tsx)。

## 新发现的放大因素：机器在线期限使用客户端时钟

Runner 每 20 秒发送一次 machine-alive，Hub 在 45 秒后判离线。旧 `MachineCache.handleMachineAlive()` 将客户端 `time` 写入 activeAt，`expireInactive()` 却拿 Hub 的 Date.now() 与它相减。慢约 17 秒的客户端使一次新心跳的实际剩余期限只有约 28 秒；正常 20 秒发送周期之外仅余约 8 秒，而不是 25 秒。这使同样的阻塞更早触发机器离线和前端自动改选。

这次增加的回归在生产旧源码上失败：收到慢 17 秒的有效心跳后，仅过 28.001 秒就变为离线。修复后机器期限使用 Hub 接收时间，保留现有时间合法性检查、namespace 授权及健康数据。新的慢时钟、续租和过期测试，以及既有机器与心跳测试共 24 项通过；Hub 类型检查通过。

**发布状态：Runner/Web 改造与 Hub 索引、心跳时钟、错误回传修复均已上线。** 更新前以 Windows 后台受限账户完成 DNS、直连 HTTPS、WebSocket 与原生目录预检。Windows 仅更换 Runner，Linux 仅重启 Hub；Codex 引擎、原生桥接、桌面应用和已有会话进程保持原 PID 与创建时间。未调整系统时钟。

源码：[机器在线判定](../../hub/src/sync/machineCache.ts)、[时钟偏差回归](../../hub/src/sync/machineCache.clock.test.ts)。

## 为什么原先的验收漏掉了

原先分别验证了搜索、模型目录、连接与正常机器在线状态，却没有把“模型缓存失效后的真实 Windows 清理成本 + 并行连接 + 心跳过期 + 前端正在等待确认”放在一个场景内。异步函数外观掩盖了内部同步命令；模型 RPC 的长超时掩盖了对同一 Runner 上其他短 RPC 的影响；同一台主机或假定时钟一致的测试没有暴露跨机器在线期限问题。

对应回归应保留三种独立证据：真实 Windows Session 0 的外部命令成本和事件循环间隔；并行目录/连接期间的心跳与请求结果；旧/新前端对瞬时离线与晚到确认的处理。只验证最终页面打开成功不能证明这些边界情况可靠。

调查证据在 `/mnt/cache/data-cache/hapi-windows-session-list-20261008/rca`：过滤后的 Hub/Nginx 请求时间线、Windows Runner 诊断、时钟采样、19 次调用的详细计时以及实验前后现有 Codex/ChatGPT PID 和创建时间。所有既有进程代际保持不变。临时探针、辅助脚本和计划任务在取回结果后清理；诊断不保存 token、请求正文或模型消息内容。


本轮追加证据位于 `/mnt/cache/data-cache/hapi-fast-catalog-20261008`：原生探针、目录/连接计时、浏览器长任务与布局记录、生产数据库只读查询计划，以及完整 Hub 测试和版本范围审计。Hub 类型检查通过，完整测试 1,467 通过、3 跳过、0 失败；CLI 和 Web 相关回归、Windows 限制令牌集成测试另有独立记录。共享工作树其他尚在开发的终端改造未进入发布版本。
