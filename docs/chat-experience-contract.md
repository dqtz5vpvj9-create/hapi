# HAPI 聊天体验升级：最终实施计划

2026-10-05 · 内容与连续性改造已发布；按用户决定，性能优化继续推进。

## 目标与范围

以 DeepSeek Harness 固定版本 5badb15009ae1756c3afe0ae0cef1faafc290ccc 为设计基线，完整迁移执行内容组织、稳定节点及阅读和导航协调，解决进入位置、更新闪烁和滚动与补页竞争。

- Linux 和 Windows 原生 Codex 一起覆盖；其他 agent 保留现有呈现。
- 连续性与内容分层全部完成并共同验收后，一次上线。内部按步骤开发，不提前发布部分改造。
- 保留 HAPI 虚拟历史、连续加载、持久书签、手机布局、主题和业务入口。
- 不增加聊天数据库副本，不扫描全部历史，不调用模型生成展示摘要，不修改模型请求。
- 移植核心及最小依赖，保留 DSH 版权和 MIT 许可，不引入其整套插件运行时。

## 架构与来源

数据流：Codex 原生历史／实时事件 → HAPI 消息窗口 → DSH 内容投影与展示规则 → HAPI 虚拟渲染与业务组件。

滚动由 DSH 的 Scroll／Reading／Navigation 协调。DOM、虚拟挂载、字符和代码位置、持久书签由 HAPI 适配层提供。每个滚动容器只有一个位置控制者。

| 部分 | 确定方案 | 来源 |
| --- | --- | --- |
| 内容语义 | Turn、内容节点、过程分组与最终答复分开，身份不依赖页序号 | DSH |
| 局部更新 | 排列 order 与按 key 订阅的节点分开，流式结算更新原节点 | DSH |
| 展示规则 | Standard 基线，移植过程分组、完成折叠、插话、停止及失败规则 | DSH |
| 滚动策略 | ChatReading、ChatNavigation、ScrollFollow 与协调顺序 | DSH |
| 长历史 | 有界窗口、连续补页、正常流与稀疏占位、阅读与跳转目标挂载 | HAPI 已有 |
| 位置保存 | 字符／代码书签、sessionStorage、版本变化后的上下文恢复 | HAPI 已有 |
| 业务组件 | 工具、产物、审批、子会话、终端、Goal、计划、附件和发送流程 | HAPI 已有 |
| 宿主接口 | 原生身份、窗口就绪、虚拟节点与实际坐标的连接 | 本次适配，逐项记录 |

原生 Codex 新正文按稳定节点渲染，不再以相邻 assistant 消息的自动合并推断执行边界。现有 composer 和内容组件继续复用。

## 行为与接口

### 执行身份和更新

贯通原生 threadId、turnId、itemId、可用的答复 phase 和真实 Turn 生命周期。历史和实时路径使用相同映射。Codex item 是内容节点，不伪造 DSH Step；缺少身份、阶段或边界时保留现有平铺内容，不启用依赖这些事实的整轮折叠。历史转换器临时包装的 completed 不是轮次结束依据。

在当前有界窗口中维护 DSH 的 order 与 keyed node source。流式增量只通知关联节点，持久结果接替时保留展示 key。元数据不创建另一份正文存储。

### 首次进入和后台更新

首次可用窗口提交与后台同步分开。可用缓存或首次成功响应（含空会话）完成打开状态；后续同步不重新初始化、不卸载已显示正文。无书签跟随末尾，有书签使用既有恢复路径。后台更新保留正文及超过 1 秒才出现的同步提示。切换会话后旧请求和旧定位回调不得作用于新会话。

不新增全文首帧屏障，不迁移 DSH 居中空会话输入框。

### 滚动和虚拟适配

迁移后的协调层决定恢复、跟随、保留和取消；新路径停用多次定时滚底与独立位置修正。布局提交和 ResizeObserver 驱动后续尺寸处理，DSH 参数先保持原值，不靠增加延时修复失败。

- 已加载但未挂载：使用 contains／reveal／pinReading，目标挂载后再定位。
- 数据在窗口外：使用既有历史上下文或目录接口，由同一导航任务完成定位。
- 原消息被撤回或删除：保留既有相邻位置恢复和提示。

连续上滑保留现有触发与预取，请求进入 DSH 导航保留流程。虚拟占位不作语义锚点；TanStack Virtual 只测量和挂载，不自行补偿或跟随。新正文仅在跟随末尾时禁用浏览器锚定；占位元素排除出候选。字符／代码恢复只执行明确的恢复任务，不与其他位置写入竞争。

### 过程、答复和交互

按 DSH 分隔进度说明、工具组和答复；符合原条件的正常完成轮次可折叠。停止、失败和插话按对应规则处理。无最终答复或完整边界时继续显示现有内容，不新增自拟结束提示。

可见内容保留稳定 key 和父节点，最终答复不随过程展开重建。需要跨虚拟卸载保存的展开状态按节点身份保留在有界展示状态中，不靠常驻全部 DOM 保存。审批、问题、产物和子会话入口不能被折叠吞掉。发送状态继续使用现有确认与原生身份匹配，不改变已处理消息的队列判定。

## 验收条件

| 场景 | 必须观察的结果 |
| --- | --- |
| 冷进入、缓存进入、历史阅读后刷新 | 首次位置符合书签或末尾意图；已有正文不退回空白加载页 |
| 后台切回、弱网、断线重连 | 保留已见内容，无重复答复、自动重发或位置重置 |
| 快速上滑时补页到达、跨越缓存窗口往返 | 无重叠、空洞、重复或遗漏，新页面不抢位置 |
| 滑动与流式增长并发 | 离开末尾后不被拉回，自己的新输入按参考规则恢复跟随 |
| 工具、代码、图片、键盘和宽度变化 | 可见节点身份稳定，阅读位置正确，控件可用 |
| 跳转后立即滚动、切会话或返回最新 | 已取消任务的晚到结果不再次定位 |
| 插话、停止、失败、审批、子代理、无最终答复 | 顺序与执行归属正确，交互和诊断内容可达 |
| 原生 App 已处理、网页重连确认 | 原消息正确结算，不重复，不重新进入队列 |

自动化检查节点身份、顺序、焦点及中间帧。受控静止补页的锚点偏移不得超过 1 CSS 像素；手势期间检查程序滚动是否违背用户意图。

同设备、同会话、同操作比较进入耗时、帧间隔、主线程耗时和内存。先测基线重复波动，再判断退步；挂载节点与窗口保持有界。共享协议变更执行仓库要求的完整类型检查、测试及受影响的原生一致性检查。浏览器模拟和真机结果分开报告，截图正常不能代替过程验收。

## 实施证据（持续更新）

- **源码已确认：**移植来源及每项适配见 [DSH 核心说明](../web/src/chat/dsh/README.md)。原有边界参数未增加延时。完整跨包类型检查已通过，Hub 1440 项通过、3 项跳过；本轮已有共享协议、Web、CLI、历史读取及 Android 一致性检查记录。iOS 工具链不可用，未宣称通过。
- **浏览器已观察：**独立构建的 58 场景首次验收通过 57 项；剩余问题是审批框先于历史出现时的 key 更换，已保留工具原生 call ID，并通过构建包复测。书签恢复改动后的 17 项回归通过 16 项，另 1 项反向连续阅读在整组运行中超时，单独复测 27.7 秒通过。验收没有通过延长产品计时器来掩盖失败。
- **真实设备已观察：**Pixel 9 Chrome 的实际拖动、补页和随后 100 帧观测中，原文字偏移最大约 0.19 CSS 像素。刷新时曾错误恢复到末尾，修复后同一书签连续 60 帧位置不变。Linux Unix socket 与 Windows Session 0 所用原生管道的只读历史探针都取得真实 thread/turn/item、phase 和轮次状态；这些探针不是发布后的完整业务链路验收。
- **性能尚未通过最终评审：**同一 Pixel 9、同一独立构建和滚动回放，三个交错的新标签页样本中，旧版主线程耗时为 1458–1547 ms，新版为 1760–1828 ms；新版 p95 帧间隔较低、受控 GC 后测试页堆约 22.3 MB（旧版约 24.0 MB）。两者最多挂载 22 行、窗口为 220 条。该实验是受控滚动回放，不是对自然手势持续帧率的承诺。CPU 增加超出基线波动，正在进一步定位。
- **发布后已观察：**Linux 和 Windows 已有会话的鉴权历史读取、桌面 Chrome 打开及刷新、新版呈现和生产资源均通过。两台机器 ID 保持不变。Pixel 9 通过校验上游 HTTPS 的主机转发读取线上资源，完成两平台会话显示和历史滚动；设备自身不信任站点证书，因此手机直连 HTTPS 仍未通过。
- **尚未验证：**手机端完整业务操作与直连证书信任，最终性能复核。

本轮临时实验记录位于缓存盘 `hapi-chat-upgrade-20261005`，不作为永久部署路径。实验未发送额外模型请求。

### 构建目录误写及恢复

一次调用把 `--config` 追加到 package build 脚本后，参数实际落在尾部复制命令，导致候选 Web 文件短暂写进线上 `web/dist`。发现后先恢复旧的内容寻址资源，再恢复入口和服务工作线程；线上 HTTPS 已确认回到原入口。新版聊天开关始终未开启，Hub、Runner 和原生引擎未因此重启。后续构建直接执行 Vite，明确指定缓存盘输出，不再经由这个含复制步骤的脚本传参。此事故发生在正式发布前；正式发布现已完成，详情如下。

## 2026-10-05 发布记录

用户决定先上线，再消除额外 CPU 开销，因此原有性能发布门槛改为发布后持续优化；不宣称性能已经验收通过。

- 两台机器的桥接程序均由 Bun 1.4.0 构建。Windows 在原 Runner 账户的 Session 0 下通过 DNS、直连 HTTPS、WebSocket 和鉴权历史检查，另外通过命名管道初始化及重连检查。
- Linux 只重启原生桥接服务；Windows 只替换原生桥接包装进程，由既有计划任务监督恢复。Windows 引擎、管道和 Runner 的进程 ID 保持不变，Hub 进程未重启。Hub 对消息元数据透明传递，无需此次替换。
- 原生 Codex 默认启用新呈现，其他 agent 维持原路径。浏览器设置 `hapi:native-chat-presentation=legacy` 后重新打开会话可以回退呈现；不会重写聊天历史。
- 发布包保存在 `/mnt/cache/build-cache/hapi-chat-release-20261005`，旧网页完整副本及 Linux 服务配置也保存在其中。Windows 旧桥接二进制保留，启动脚本备份为 `config/start-hapi-before-chat-20261005.ps1`。
- 网页先发布内容寻址资源，再原子替换入口及服务工作线程；旧资源保留供已打开的客户端使用。首次上线入口为 `index-BYRYnvmP.js`；性能与焦点修复后更新为 `index-DUdGp1mb.js`。
- CPU 采样发现当前轮次探测重复捕获字符级书签，以及阅读状态变化带动消息组件重渲染。已改用外层行边界探测，稳定虚拟列表、初始阅读锚点及业务 Context 的 React 身份；DSH 的采样间隔和跟随规则保持不变。

## 发布后的性能优化与回归

这一轮 Web 优化已经发布，不重启 Hub 或原生引擎。补充修复了过程结算时虚拟范围变化导致提问框卸载的问题：有焦点的消息行会保留挂载，直到焦点离开。工具身份仍使用原生 call ID。

独立构建的完整 58 项浏览器回归全部通过，包括代码和字符书签、历史跨窗口往返、切会话取消晚到导航、过程折叠、最终答复身份及提问草稿。Web 类型检查及 18 项相关组件／投影测试通过。此前代码书签复测出现过一次失败，稳定初始锚点后连续 5 次专项复测及本轮整组测试通过；不把一次最终截图当作修复证据。

Pixel 9 Chrome 151，同一 1200 条合成会话、100 帧双向滚动回放，交错运行三次旧版和三次优化版：

| 指标 | 旧版 | 优化后的新版 |
| --- | --- | --- |
| 主线程耗时中位数 | 1488 ms | 1604 ms（约 +7.8%） |
| 主线程三次范围 | 1486–1511 ms | 1579–1644 ms |
| p95 帧间隔范围 | 43.2–44.8 ms | 25.0–27.3 ms |
| 首次末尾可见耗时中位数 | 687 ms | 634 ms |
| 受控 GC 后测试页堆 | 24.0–24.2 MB | 21.5 MB |
| 最大挂载行数／窗口消息数 | 22／220 | 22／220 |

初版额外 CPU 开销约 20%，本轮降到约 8%。剩余差距仍高于这组基线波动，不能宣称开销已经完全消除。帧间隔与主线程总耗时衡量不同问题；此回放不是自然手势的持续 FPS 或整机内存评测。

另一个“只减少当前轮次 React 通知”的候选没有带来稳定收益，已撤销；减少 DOM 包装层的候选也已撤销。发布保留有证据的改动。记录：缓存盘 `release/pixel-performance-context.json`、`release/context-browser-all.log`；设备及测试方法与前述证据边界一致。
